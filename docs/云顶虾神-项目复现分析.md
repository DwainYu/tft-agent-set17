### 一、产品功能拆解

从四张截图可以还原出产品的完整交互链路，分为以下几个层次：

**1. 对话式交互层**

产品是一个聊天界面的 AI 助手。用户输入自然语言问题（如"龙王+加里奥阵容"），系统返回结构化的数据卡片和自然语言摘要。左侧边栏管理会话历史，支持新建对话、登录态持久化。

底部有四个提问方向标签：推荐阵容、推荐装备、查专属、检索装备。截图中的黄色提示气泡说明了一个关键设计——用户需要先选方向再提问，这降低了意图分类的难度，也引导用户给出更精确的输入。

**2. 推理过程可视化**

第二张截图展示了"思考过程"面板，分为三个可折叠的阶段：

- "虾神正在理解你的问题" — 意图识别和实体匹配的结果（如把"龙王"解析为"奥瑞利安·索尔"，cost 4，霸天机甲/神谕）
- "虾神在挑选工具，查询数据" — 工具选择和执行的子步骤（查阵容 → 查符合条件的阵容 → 整理结果）
- "虾神正在组织回答" — 数据来源和策略说明（使用了 query_tft_comps_library 工具，返回 5 个阵容）

这本质上是一个 Agent 的 ReAct 模式（Reasoning + Acting），但把中间过程暴露给了用户。这不仅是技术需求，也是产品差异化——让用户看到"虾神在想什么"，增加信任感和趣味性。

**3. 阵容推荐卡片**

第三张截图是核心输出，一张高度结构化的阵容卡片，包含：

- 英雄头像行（9 个英雄）+ 角色标签（主C / 副C / 主坦 / 副坦）
- 羁绊标签行（6 暗星、2 旅人、2 斗士...）
- 每个英雄下方的装备小图标
- 三个子区块：纹章推荐（带数值影响分）、神器·异常（带数值影响分）、变阵建议（人口+替补英雄）
- 底部自然语言总结（平均排名 4.3，样本量两万二，出装建议）

这张卡片的信息密度很高，数据来源于阵容库查询 + 英雄/装备/羁绊静态数据的拼接。

**4. 用户认证系统**

tftai.cn 的登录页面（/login）提供了一套完整的手机号注册登录体系，标题为"账号中心 — 云顶虾神"，支持三种认证方式：

- 密码登录：手机号 + 密码
- 验证码登录：手机号 + 短信验证码
- 注册：手机号 + 短信验证码 + 设置密码（至少 6 位），注册后自动登录

设计上是独立的登录页（非弹窗），居中白色卡片 + 浅米色背景，Tab 切换"登录"和"注册"两个表单。登录态和侧边栏的"会话"历史功能联动——截图1中侧边栏底部有"登录"按钮，提示"登录后会在这里显示你的历史对话"，说明未登录状态下可以正常使用，但对话历史不会跨设备同步。

### 二、现有资产盘点

tft-agent-set17 项目已经积累了一批可直接利用的数据资产：

**真实对局数据**：通过 Riot API 从 JP1 服务器采集的 427 场 Challenger 排位赛（2026/7/11-13），清洗后的 5 张 CSV 覆盖了 matches、participants、units、traits、items 五个维度。这是计算装备 delta 值、阵容胜率等统计数据的一手数据源。

**Data Dragon 静态资源**：完整的 Set 17 英雄/装备/羁绊/强化数据（中英文 JSON），以及全套图标 PNG（英雄头像、装备图标、羁绊图标、强化图标）。这些是阵容卡片渲染和 `character_id → 中文名` 映射的基础。

**数据采集脚本**：`data_collection/scripts/` 下有完整的采集管线（Challenger 列表 → 对局 ID → 对局详情），支持增量采集和 SQLite 存储，可以定期刷新数据。

具体来说：

| 资产 | 位置 | 状态 | 对复现的价值 |
|------|------|------|-------------|
| Data Dragon 静态数据 | `asset/data/zh_CN/` | 已有 JSON | 英雄/装备/羁绊名称和 ID 映射 |
| Data Dragon 图标 | `asset/img/` | 已有 PNG | 英雄头像、装备图标、羁绊图标、强化图标 |
| 真实对局数据 | `data_collection/data/cleaned/` | 已清洗 CSV | 可用于计算装备 delta 值、阵容统计 |
| 对局原始数据 | `data_collection/data/raw/` | SQLite DB | 471 场对局的完整 JSON，支持增量更新 |
| 数据采集脚本 | `data_collection/scripts/` | 已实现 | Challenger 采集 → 对局详情 → 数据清洗全链路 |

**尚需补充的数据**：

- 阵容库数据（如 MetaTFT 的 comp_details），提供阵容级别的推荐信息（英雄组合、平均排名、样本量、纹章、变阵）
- 装备 delta 值的聚合统计（需要从对局数据中计算）
- 英雄别名字典（昵称/拼音/英文 → 官方中文名，如"龙王" → "奥瑞利安·索尔"）

### 三、技术栈选型

#### 3.1 前端

截图中的 UI 是一个现代的单页应用，特征是：浅色主题、圆角卡片、柔和阴影、响应式布局、可折叠面板、英雄头像网格、羁绊标签药丸、装备小图标。

**方案 A：React + Tailwind CSS（推荐）**

React 组件化天然适合这种结构化卡片渲染。阵容卡片、英雄头像、羁绊标签、装备图标都是独立组件，组合复用。Tailwind 处理圆角/阴影/配色效率高，不需要写大量 CSS。推理过程的折叠面板、流式输出、状态管理都有成熟的方案。

**方案 B：Vue 3 + Tailwind CSS**

和方案 A 类似，Vue 的模板语法对中文开发者更友好，但生态中针对聊天 UI 的组件库略少于 React。

结论：推荐 React + Tailwind。如果更熟悉 Vue，Vue 3 + Tailwind 也完全可行。

#### 3.2 后端

推荐使用 FastAPI + SQLite，理由是：Python 生态与现有采集脚本统一、FastAPI 原生支持 async 和 SSE、SQLite 自包含免运维、项目初期不需要复杂的数据库方案。

**核心架构**：

```
用户请求 → 意图路由 → 实体匹配 → 工具调度 → 数据查询 → 结果组装 → SSE 流式返回
```

**需要实现的模块**：

- **意图路由器（Router）**：根据用户输入 + 前端传入的 `direction` 参数，判断意图类型（推荐阵容 / 推荐装备 / 查专属 / 检索装备）
- **实体匹配器**：从自然语言中提取英雄/装备/羁绊名称，处理别名映射（龙王 → 奥瑞利安·索尔）
- **工具系统（Tools）**：根据意图调用对应的数据查询函数，如 `query_comps(champions=[...])` 查询阵容库
- **流式响应（SSE）**：把推理过程分阶段推送给前端，而非一次性返回最终结果

#### 3.3 数据层

需要整合多个数据源，形成统一的数据服务：

```
┌─────────────────────────────────────────────────┐
│               统一数据层                          │
│                                                   │
│  ┌──────────────┐  ┌──────────────┐  ┌─────────┐│
│  │ 静态数据      │  │ 阵容库       │  │对局统计  ││
│  │ (Data Dragon) │  │ (MetaTFT)    │  │(Riot API)││
│  │              │  │              │  │          ││
│  │ 英雄/装备/   │  │ 阵容组合/    │  │装备delta ││
│  │ 羁绊/强化    │  │ 排名/样本量  │  │阵容胜率  ││
│  │ 图标路径     │  │ 纹章/变阵    │  │英雄统计  ││
│  └──────────────┘  └──────────────┘  └─────────┘│
│         │                │              │         │
│         └────────────────┴──────────────┘         │
│                       │                           │
│              SQLite (统一 DB)                      │
│              + FTS5 全文索引                       │
│              + 图标文件本地服务                     │
└─────────────────────────────────────────────────┘
```

关键数据整合点：

- Data Dragon 的 `champion.json` 提供 `character_id → 中文名 + 费用 + 图标路径` 的映射，用来补全 Riot API 数据中 `unit.name` 为空的问题。
- MetaTFT 的 `comp_details` 提供阵容级别的推荐数据（英雄组合、装备、纹章、平均排名），这是截图3阵容卡片的直接数据源。需要实现 MetaTFT 数据采集脚本（`cluster_id=409` 对应 Set 17）。
- Riot API 的对局数据可以用来计算装备 delta 值和实时统计，补充 MetaTFT 没有的维度。

#### 3.4 图标资源服务

Data Dragon 的图标需要本地化服务：

- 将 `asset/img/` 下的 PNG 文件复制到后端的 static 目录
- 通过 FastAPI 的 StaticFiles 挂载提供 HTTP 访问
- 前端通过 `/assets/champion/{id}.png` 等路径引用

#### 3.5 用户认证

tftai.cn 的认证系统需要以下后端能力：

**用户存储**：在 SQLite 中新建 `users` 表（phone, password_hash, created_at, last_login_at）。密码用 bcrypt 或 argon2 哈希存储，绝不明文。

**短信验证码**：需要接入国内短信服务商（阿里云短信、腾讯云短信、容联云等）。验证码存 Redis 或 SQLite（带过期时间），推荐 Redis 因为自带 TTL 机制。考虑到项目初期用户量不大，SQLite + 定时清理也能工作。

**JWT 会话管理**：登录成功后签发 JWT（access_token + refresh_token），前端存 httpOnly cookie 或 localStorage。FastAPI 有成熟的 `python-jose` / `PyJWT` 方案。

**路由守卫**：`/ask` 等核心接口可以匿名访问（未登录也能用），但 `/conversations` 等会话管理接口需要鉴权。中间件层通过 JWT 解析 user_id，关联到 conversation 表。

**数据模型**：

```
users 表: id, phone, password_hash, created_at, last_login_at
conversations 表: id, user_id (FK, nullable), title, created_at, updated_at
messages 表: id, conversation_id (FK), role (user/assistant), content, metadata_json, created_at
champions 表: id, character_id, name_cn, name_en, cost, traits_json, icon_path
items 表: id, name_cn, name_en, icon_path, type
synergies 表: id, name_cn, name_en, icon_path, tiers_json
comps 表: id, name, champions_json, synergies_json, avg_placement, sample_size, emblems_json, artifacts_json, flex_slot_json
item_stats 表: id, item_id, champion_id, delta_rank, sample_size
```

`conversations.user_id` 设为 nullable，允许未登录用户的临时会话存在内存/localStorage 中，登录后再合并到服务端。

### 四、核心功能实现路径

#### 4.1 意图分类 + 实体匹配

需要实现一个意图路由器，核心是基于关键词 + 别名字典的规则匹配：

**意图分类**：前端传入 `direction` 参数（推荐阵容 / 推荐装备 / 查专属 / 检索装备）作为强约束，后端可以直接用它确定意图类型，大幅降低分类难度。如果 `direction` 为空，则回退到关键词匹配。

**实体匹配**：维护一张别名字典，覆盖英雄/装备/羁绊的昵称、拼音、英文名到官方中文名的映射。截图中的"龙王→奥瑞利安·索尔"就是通过别名字典完成的。需要从 Data Dragon 的 `champion.json` 自动生成基础映射，再手工补充常见别名。

#### 4.2 推理过程流式输出

截图中的推理过程是分阶段展示的，后端需要通过 SSE（Server-Sent Events）流式输出：

```
POST /ask → SSE stream

Event 1: { "stage": "understanding", "content": "用户问的是龙王+加里奥阵容..." }
Event 2: { "stage": "tool_selection", "content": "虾神决定查阵容" }
Event 3: { "stage": "tool_execution", "content": "虾神在查符合条件的阵容" }
Event 4: { "stage": "tool_done", "content": "虾神查完了，正在整理结果" }
Event 5: { "stage": "composing", "content": "使用 query_tft_comps_library，返回 5 个阵容..." }
Event 6: { "stage": "result", "data": { "card": {...}, "summary": "..." } }
```

每个 stage 对应截图2中的一个可折叠面板。前端收到后逐步展开。FastAPI 的 `StreamingResponse` + `text/event-stream` 可以实现这个需求。

#### 4.3 阵容卡片数据结构

截图3的阵容卡片需要一个复合数据结构：

```json
{
  "comp_name": "暗星·奥瑞利安·索尔",
  "avg_placement": 4.3,
  "sample_size": 22000,
  "champions": [
    {
      "name": "奥瑞利安·索尔",
      "role": "主C",
      "cost": 4,
      "icon": "/assets/champion/TFT17_AurelionSol.png",
      "items": ["珠光护手", "暗星纹章", "..."],
      "traits": ["霸天机甲", "神谕"]
    }
  ],
  "synergies": ["6 暗星", "2 旅人", "2 斗士", "..."],
  "emblems": [
    { "name": "旅人纹章", "target": "卡莎", "delta": -0.47 }
  ],
  "artifacts": [
    { "name": "阿里的光环", "target": "奥瑞利安·索尔", "delta": -0.61 }
  ],
  "flex_slot": { "population": 10, "champion": "巴德" }
}
```

这个结构需要后端把阵容库数据 + Data Dragon 英雄/图标数据 + 装备 delta 数据拼接后返回。

#### 4.4 装备 Delta 值

截图中的数值（-0.47、-0.61 等）是装备对平均排名的影响值。计算方式：

```
delta = avg_placement(有该装备) - avg_placement(无该装备)
```

负值表示有该装备时排名更好（数字越小排名越高）。

这个数据有两个来源：MetaTFT 的大样本数据（两万二样本）更可信，优先使用；tft-agent-set17 的 Riot API 对局数据（427 场 / 75 个 Challenger 玩家）作为补充和验证。需要实现一个 delta 值的聚合计算脚本，从清洗后的 CSV 或 SQLite 中提取。

**Phase 2 — 数据补全 + 其他方向（约 1.5 周）**

核心目标：补全截图中的所有数据维度和查询方向。

- 实现纹章推荐和神器·异常数据

- 补全其他 3 个方向的查询能力（推荐装备、查专属、检索装备）
- 自然语言摘要生成（模板化 or LLM）
- FTS5 全文检索（支持中文搜索英雄/装备/羁绊）

**Phase 3 — 体验优化（约 1 周）**

- 推理过程面板的折叠/展开交互
- 移动端适配
- 错误处理和边界情况

- 数据刷新机制（定期更新 MetaTFT 和 Riot API 数据）

### 六、实施注意点

**6.1 数据一致性**

Data Dragon 的英雄 ID 格式是 `TFT17_AurelionSol`，MetaTFT 用自己的 comp_id，Riot API 的 character_id 也是 `TFT17_*` 但 `unit.name` 为空。需要建立一张统一的英雄映射表，确保三方数据能正确 JOIN。

**6.2 MetaTFT 数据的时效性**

截图中的阵容数据（平均排名 4.3、样本量两万二）来自 MetaTFT。MetaTFT 的数据需要定期更新以保持和当前版本同步。需要实现 MetaTFT 采集脚本，并设计定时刷新机制。注意 MetaTFT 的 `cluster_id=409` 对应 Set 17。

**6.3 图标资源管理**

Data Dragon 的图标是按版本发布的，每次版本更新后图标路径可能变化。建议把图标复制到本地并建立 `character_id → 本地路径` 的映射表，不要依赖 CDN 热链接。`asset/img/champion/` 下已有完整的英雄头像 PNG。

**6.4 SSE 流式响应设计**

流式输出的粒度需要仔细设计。太粗（只推 2-3 个事件）用户感知不到"思考过程"；太细（每个 DB 查询都推一次）会导致前端频繁重渲染。建议按截图中的 3 阶段 + 最终结果共 4-6 个事件来推。

**6.5 中文全文检索**

SQLite FTS5 的 unicode61 分词器对中文有已知问题（连续中文被当作单 token）。解决方案是用全子串生成 + 停用词过滤来实现中文搜索。所有需要搜索的表（英雄、装备、羁绊）都要同步建立 FTS5 索引，并验证中文搜索质量。

**6.6 SQLite 唯一约束限制**

SQLite 不支持 `ALTER TABLE ADD COLUMN ... UNIQUE`。如果需要在已有表上加唯一约束列，要先加普通列再建 `CREATE UNIQUE INDEX ... WHERE col IS NOT NULL`。

**6.7 Windows 开发环境**

Rich 库的 spinner 字符（Braille 等）会触发 GBK 编码错误，需要设置 `PYTHONUTF8=1` 和 `PYTHONIOENCODING=utf-8`。FastAPI 的 `dev --port` 参数可能不生效，建议用 `uv run uvicorn api.app:app --host 0.0.0.0 --port 8002`。

**6.8 LLM 集成的取舍**

意图分类可以纯规则实现（关键词 + 别名字典），但截图中"虾神正在理解你的问题"的输出格式暗示可能有 LLM 参与（把规则匹配结果包装成自然语言描述）。可以考虑在推理过程描述和自然语言摘要生成两个环节引入 LLM，但核心的数据查询仍走工具系统，确保数据准确性。

**6.9 短信服务选型**

国内短信验证码服务商的选择需要考虑：到达率、延迟、价格和审核流程。主流选项包括阿里云短信（到达率高，审核严格）、腾讯云短信（和微信生态整合好）、容联云（价格较低）。验证码有效期建议 5 分钟，同一手机号 60 秒内不可重复发送，每日上限 10 条。正式上线前需要在服务商后台完成短信模板审核（通常 1-2 个工作日）。

**6.10 安全基线**

即使是小型项目，认证相关的安全基线不能省：密码必须哈希存储（bcrypt cost factor >= 10）；JWT 签名用 HS256 + 随机 secret（不要硬编码在代码中，放 .env）；接口限流防止暴力破解（登录接口 5 次/分钟/IP）；短信接口必须做防刷（IP 限频 + 手机号限频 + 可选图形验证码前置）。

### 七、风险识别

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| MetaTFT 数据源不稳定或变更 API | 阵容数据无法更新 | 本地缓存 + 多源备份，Riot 对局数据作为 fallback |
| 对局数据样本量不足（仅 427 场） | delta 值不可信 | 优先用 MetaTFT 的大样本数据，Riot 数据只做补充 |
| Set 17 版本更新导致数据失效 | 英雄/装备/羁绊变更 | 数据刷新脚本 + 版本检测机制 |
| SSE 流式响应在弱网下体验差 | 推理过程中断 | 设计降级方案：超时后一次性返回完整结果 |
| 前端阵容卡片在移动端显示困难 | 9 个英雄 + 大量数据挤在小屏 | 横向滚动 + 折叠详情，参考截图3的桌面端设计做适配 |
| 短信验证码被刷量 | 产生高额短信费用 | IP/手机号双重限频 + 图形验证码前置 + 每日上限 |
| 短信模板审核周期 | 注册功能无法按时上线 | 提前提交审核，开发期先用固定验证码 mock |
| 用户数据合规（手机号属个人信息） | 法律风险 | 隐私政策页面、手机号脱敏展示、数据删除能力 |

### 八、总结

复现"云顶虾神"的核心工作量集中在四块：数据层建设（Data Dragon 静态数据导入 + MetaTFT 阵容采集 + 装备 delta 计算 + 别名映射）、用户认证系统（手机号注册/登录 + 会话持久化）、Agent 后端（意图路由 + 工具调度 + SSE 流式推理输出）、前端重建（React 聊天 UI + 阵容卡片组件）。

tft-agent-set17 的 Data Dragon 资源（中英文 JSON + 全套图标 PNG）和对局数据是现成的原材料，省去了从零采集的工作量。主要的新开发工作集中在：MetaTFT 阵容数据采集、Agent 推理引擎、SSE 流式接口、前端 UI 和用户认证系统。

建议按 Phase 0 → 1 → 2 → 3 的顺序推进。Phase 0 先把数据层和认证基础设施搭好（短信模板审核需要提前提交），Phase 1 跑通"提问 → 流式推理 → 阵容卡片"的最小链路，验证整体方案可行后再逐步补全数据维度和体验优化。
