# 02 · 优化实战案例集

> 这份文档记录项目里**真实遇到的问题**，以及"问题 → 定位 → 优化 → 验证"的完整过程。
> 它的价值不在于"这些 bug 本身"，而在于**沉淀一套可迁移的工程方法论**。
> 技术栈会过时，但"怎么定位并解决一个陌生问题"的能力不会。

这是一份**活文档**：以后每遇到一个值得记录的问题，就用文末的模板补一条进来。

---

## 0. 方法论：四步闭环

遇到任何问题（性能、报错、行为异常），都按这四步走，**不要跳步**：

```
① 问题（Problem）   →  准确描述"现象"，最好能量化（多慢？错在哪一行？）
② 定位（Diagnose）  →  找到"根因"，而不是停在"表象"。多问几个为什么。
③ 优化（Fix）       →  针对根因设计改法，并想清楚 trade-off 和副作用。
④ 验证（Verify）    →  用证据证明问题真的解决了，而不是"我觉得好了"。
```

**最常见的错误是跳过 ② 直接做 ③**——看到慢就加缓存，看到报错就 try/except 吞掉。没有定位的优化，往往治标不治本，甚至引入新 bug。

另一个关键原则：**先测量，再优化（Measure before you optimize）。** 在没搞清楚"时间到底花在哪"之前，任何优化都是猜。下面 Case 001 会完整演示这一点。

## Case 001 · RAG 模型每次调用都重新加载（性能）

> 状态：**已应用** ｜ 难度：★★☆☆☆ ｜ 涉及链路：RAG ｜ 收益：极大（数十秒 → 数百毫秒）

### ① 问题

测试 Agent 多工具组合时，发送"锐雯主 C 配什么装备"，请求**超过 90 秒超时**。
日志显示 Agent 逻辑本身正常（Planner 选了 2 个工具、Critic 还触发了重试），但整体就是慢得离谱。

**量化现象**：一次本应几秒完成的请求，耗时 > 90s 且未返回。

### ② 定位

第一步不是猜，而是**缩小范围**。请求慢，可能慢在：网络？LLM 推理？工具执行？数据库？

观察日志里各阶段的耗时，发现慢点集中在 `rag_search` 这个工具被调用之后。于是去看它的实现（`api/agent/tools.py`）：

```python
def _rag_search(self, query: str, top_k: int = 5) -> list[dict]:
    try:
        from api.services.rag.engine import RAGEngine
        from api.services.rag.embedding import BGEEmbedding
        from api.services.rag.reranker import BGEReranker

        embedding = BGEEmbedding()      # ← 每次调用都 new
        reranker = BGEReranker()        # ← 每次调用都 new
        engine = RAGEngine(embedding=embedding, reranker=reranker)  # ← 每次调用都 new
        docs, latency = engine.query(query, top_k=top_k)
        return [...]
    except Exception as exc:
        ...
```

**表象**：每次调 `rag_search` 都新建三个对象。
**但这还不是根因**——新建对象本身很便宜。继续追问：新建 `BGEEmbedding()` 会发生什么？

去看 `api/services/rag/embedding.py`：

```python
class BGEEmbedding:
    def __init__(self, ...):
        self._model: Any = None          # 构造时只是置 None，很轻

    def _ensure_model(self):             # 真正的加载在这里
        if self._model is None:
            self._model = BGEM3FlagModel(self._model_name, ...)  # ← 加载几个 G 的模型！

    def encode(self, texts, ...):
        self._ensure_model()             # 第一次 encode 时才触发加载
        ...
```

**根因找到了**：`BGEEmbedding` 内部做了"懒加载"——模型不在构造时加载，而是第一次 `encode` 时才加载，并缓存到 `self._model`。这个设计本身是对的，**但它缓存的是"实例级"状态**。而 `_rag_search` 每次都新建实例，新实例的 `self._model` 永远是 `None`，于是**每次 `query()` 都触发一次完整的模型加载**。函数返回后实例被回收，几个 G 的权重读进来又扔掉，下次重来。

用一句话概括根因：

> **懒加载 + 一次性实例 = 每次都走最慢路径。缓存被挂在了生命周期最短的对象上。**

**为什么加载这么慢？** BGE-M3 磁盘权重约 4.3GB，加载要：读文件 → 反序列化 → 构建计算图 → 放入内存，实测数十秒。而真正编码一次 query 只要几百毫秒。也就是说，**99% 的时间花在"搬模型"，而不是"算向量"**。这就是"先测量"的意义——如果不看耗时分布，你可能会误以为是"向量计算慢"而去优化错误的地方。

### ③ 优化

**目标**：让模型在整个进程里只加载一次，所有 `rag_search` 调用复用同一个已加载的实例。这就是**单例（Singleton）模式**的典型应用场景。

**为什么这里适合单例？** 因为 BGE-M3 模型是**无状态的纯函数**——给文本、返回向量，权重只读，不保存任何请求相关的东西。这种"构建昂贵 + 只读复用"的对象，是单例最经典的适用场景。（反例：数据库事务对象携带请求状态，就绝不能单例。）

**方案**：加一个进程级的缓存工厂，用 `functools.lru_cache` 实现（推荐，理由见下）。

新增工厂函数（可放在 `api/services/rag/engine.py` 或单独的 `registry` 模块）：

```python
from functools import lru_cache

@lru_cache(maxsize=1)
def get_rag_engine() -> "RAGEngine":
    """进程级单例：模型只加载一次，后续调用复用同一实例。"""
    return RAGEngine(embedding=BGEEmbedding(), reranker=BGEReranker())
```

然后 `_rag_search` 改成：

```python
def _rag_search(self, query: str, top_k: int = 5) -> list[dict]:
    try:
        from api.services.rag.engine import get_rag_engine
        engine = get_rag_engine()          # ← 复用单例，不再每次 new
        docs, latency = engine.query(query, top_k=top_k)
        return [
            {"content": d.content, "score": d.score, "metadata": d.metadata}
            for d in docs
        ]
    except Exception as exc:
        logger.warning("rag_search unavailable: %s", exc)
        return [{"content": f"RAG 服务暂不可用: {exc}", "score": 0, "metadata": {}}]
```

注意：**`BGEEmbedding`/`BGEReranker` 类本身一行都不用改**。它们内部的 `_ensure_model` 懒加载逻辑，在单例语义下恰好是正确的——实例只建一次，模型也只载一次。我们只是把"实例的生命周期"从"一次调用"提升到了"整个进程"。

**为什么选 `lru_cache` 而不是手写全局变量？** 三种写法效果等价，但 `lru_cache` 有两个实际优势：

1. **线程安全**。uvicorn 用线程池跑同步代码时，两个请求可能同时看到"还没初始化"，手写 `global` 会各自加载一次（瞬间两份权重进内存）。`lru_cache` 在 CPython 下对同一 key 的并发调用有内部锁，**不会重复执行函数体**。
2. **异常不缓存**。如果第一次加载失败（比如 Milvus 没起）抛了异常，`lru_cache` **不会**把这个失败缓存下来，下次调用会重试加载。这比"缓存一个坏实例"行为更合理。

**trade-off 与副作用**（必须想清楚）：

- **内存常驻**：模型加载后永久驻留内存（fp32 下 BGE-M3 约 2.3GB+，加 reranker 几百 MB），不再用完释放。这是用内存换延迟，服务器场景的正常代价。要确认机器内存够。
- **首次调用仍慢**：单例默认还是"第一次调用才加载"，第一个触发 RAG 的用户仍要等数十秒，只是之后的人快。如果想让服务启动时就加载好，可在 FastAPI 的 `startup` 事件里预热（调一次 `get_rag_engine()` 并 encode 一段文本）。代价是启动变慢、且即使从不用 RAG 也占内存。当前场景保持懒加载即可。

### ④ 验证

优化不能停在"改完了"，要用证据证明：

1. **功能验证**：重启服务，连续发两次开放式问题（如"新手怎么玩"）。第一次仍慢（加载模型），**第二次应在数百毫秒级返回**——这就证明模型被复用了。
2. **日志验证**：`embedding.py` 里有 `logger.info("Loading BGE-M3 model ...")`。优化前每次调用都打印这行；优化后**整个进程生命周期只应打印一次**。
3. **之前的超时场景**：重发"锐雯主 C 配什么装备"，确认不再 90s 超时。

> **已应用**：改动已落地。你可以用这三种方式验证效果：
> 1. 重启服务，连续发两次开放式问题（如"新手怎么玩"），第二次应在数百毫秒级返回。
> 2. 观察日志：`Loading BGE-M3 model ...` 整个进程生命周期只应打印一次。
> 3. 重发"锐雯主 C 配什么装备"，确认不再 90s 超时。

### 这个案例教会我们什么

- **缓存要挂在正确的生命周期上**。实例级缓存配一次性实例 = 没缓存。
- **懒加载不是免费的**，它只是把成本推迟；如果对象用完即弃，推迟的成本每次都要付。
- **先测量耗时分布，再决定优化点**，否则会优化错地方。
- **单例适用于"昂贵构建 + 只读复用"的无状态对象**。

## Case 002 · 英雄头像被裁掉（UI 还原）

> 难度：★☆☆☆☆ ｜ 涉及链路：前端 ｜ 收益：体验修复

**① 问题**：阵容卡片上的英雄头像"没展示全"，人物被切得只剩局部。

**② 定位**：先看素材真实尺寸——Data Dragon 的英雄原画是 **256×128 的横图（2:1）**。而 `HeroAvatar` 组件用 48×48 正方形容器 + `object-cover`，浏览器为了填满正方形，把横图上下大量裁掉，人物主体被切。

**③ 优化**：把容器改成匹配原画比例的宽矩形（`w-16` / 图 `h-12 w-16`），并用 `object-top` 让裁剪时保留上半身（人物通常在画面上方）。

**④ 验证**：刷新页面看截图，英雄上半身完整显示。

**教训**：**UI 还原要先看素材的真实尺寸比例**，别想当然用正方形。这类问题单元测试测不出来，只能靠"看实际渲染效果"发现——所以前端一定要有"截图核对"这一步。

## Case 003 · Windows 下打印中文/emoji 报 GBK 错（环境）

> 难度：★☆☆☆☆ ｜ 涉及链路：脚本/环境 ｜ 收益：脚本能跑

**① 问题**：在 Windows cmd 跑 Python 脚本，打印含中文或 emoji 的内容时抛 `UnicodeEncodeError: 'gbk' codec can't encode character`。

**② 定位**：Windows 控制台默认编码是 GBK，无法编码部分 Unicode 字符（尤其 emoji）。Python 往 stdout 写时按 GBK 编码就炸了。

**③ 优化**：用 `python -X utf8` 运行，或在脚本开头 `sys.stdout.reconfigure(encoding='utf-8', errors='replace')`，把输出编码强制为 UTF-8。

**④ 验证**：重跑脚本，中文/emoji 正常输出。

**教训**：**编码问题几乎都是"默认编码 ≠ 你以为的编码"**。跨平台脚本要显式指定编码，不要依赖系统默认。

## Case 004 · Git Bash 把 `/PID` 当成路径（环境）

> 难度：★☆☆☆☆ ｜ 涉及链路：环境/Shell ｜ 收益：命令能跑

**① 问题**：在 Git Bash 里执行 `taskkill /PID 1234 /F`，报错说找不到 `C:/Program Files/Git/PID`。

**② 定位**：Git Bash 会把以 `/` 开头的参数自动转换成 Windows 路径（MSYS 的路径转换机制），`/PID` 被误当成路径。

**③ 优化**：改用 PowerShell 原生命令 `powershell.exe -Command "Stop-Process -Id 1234 -Force"`，绕开 MSYS 转换。

**④ 验证**：进程被正常结束。

**教训**：**在 Windows 的类 Unix shell 里，`/xxx` 形式的参数有被路径转换的风险**。遇到诡异的路径报错，先怀疑 shell 的参数转换，换用原生 PowerShell 往往最干净。

## Case 005 · rag_search 从来没真正连上过 Milvus（架构/健壮性）

> 状态：**已修复** ｜ 难度：★★★☆☆ ｜ 涉及链路：RAG/Agent ｜ 收益：RAG 链路从"假的"变"真的"

Case 001 解决了"模型重复加载"，但把单例工厂真正落地时，暴露出一个更深的问题：**Agent 的 `rag_search` 工具从来就没有检索过 Milvus——它一直在空转。**

### ① 问题

给 `/internal/rag/query` 端点做联调时发现：直接调端点有结果，但 Agent 走 `rag_search` 工具永远返回空或"暂不可用"。同一个 `RAGEngine`，两条调用路径行为不一致。

**量化现象**：Milvus 里明明灌了 481 篇文档，Agent 侧检索结果恒为 0 条。

### ② 定位

对比两条路径的构造代码，差异一目了然。端点侧（修复前）和工具侧各自**独立手工组装** engine：

```python
# api/agent/tools.py（旧代码）
embedding = BGEEmbedding()
reranker = BGEReranker()
engine = RAGEngine(embedding=embedding, reranker=reranker)   # ← 没传 milvus！
```

而 `RAGEngine.__init__` 里 `self.milvus = milvus or MilvusStore()`——不传就 new 一个**从未 `connect()` 过**的 `MilvusStore`，它的 `_collection` 永远是 `None`，`dense_search` 静默返回空列表。**没有报错、没有日志，只是永远查不到东西**——这是最危险的一类 bug：静默失败。

根因一句话：

> **同一个对象的组装逻辑散落在多个调用点，每个点各自漏装一个零件，而且漏掉的那个零件失败时不发声。**

顺着排查还发现第二层问题：即便接上了 Milvus，`reranker.rerank()` 也会炸——reranker 模型没有 vendored 到本地，运行时尝试从 HuggingFace 下载，环境网络不通（SSL 校验失败）。如果让整个 `query()` 抛异常，检索结果就全丢了，可实际上**检索（retrieve）和精排（rerank）是两个独立阶段，精排失败不该连累检索**。

### ③ 优化

两刀切下去：

**第一刀：收敛组装点。** 全项目只留一个构造入口——`engine.py` 里的 `get_rag_engine()`（`lru_cache` 单例，见 Case 001），由它统一完成"embedding + reranker + Milvus 连接 + 集合加载 + 可选 Neo4j"的完整装配。路由层和工具层都改为 `from api.services.rag.engine import get_rag_engine`，**删掉所有本地手工组装**。组装逻辑只有一份，就不会再出现"这边接了那边没接"。

**第二刀：分阶段降级。** 区分"必需依赖"和"增强依赖"：

- Milvus 是必需的：连接失败就抛异常（`lru_cache` 不缓存异常，下次调用自动重试，服务可以先起来、Milvus 后到）。
- reranker 是增强的：`rerank()` 包一层 try/except，失败时打日志并**退回 RRF 融合序**返回结果——分数置 0 但内容照给：

```python
if rerank and unique:
    try:
        scored = self.reranker.rerank(query_text, unique, top_k=top_k)
    except Exception as exc:
        logger.warning("Reranker unavailable (%s); returning RRF-ordered results", exc)
        scored = [ScoredDocument(content=c["content"], score=0.0, metadata=c["metadata"])
                  for c in unique[:top_k]]
```

这就是 RAG 系统该有的**优雅降级（graceful degradation）**：外部依赖一个个失效，服务能力一层层退化，但永远不整链路崩掉。

### ④ 验证

1. 真实检索：`ToolRegistry.execute("rag_search", {"query": "锐雯主C配什么装备"})` 返回 5 条来自 `tft_documents_v2` 的文档，带 `source` 溯源元数据（此前恒为空）。
2. 降级路径：reranker 加载失败时日志出现 `Reranker unavailable ... returning RRF-ordered results`，查询仍有结果返回。
3. 单测固化：`tests/unit/test_agent_tools.py` 的降级用例改为 patch 工厂函数抛异常（不依赖"服务恰好没起"），保证在任何环境都可复现。

**教训**：

- **静默失败比报错更可怕**。依赖缺失时要么大声报错，要么明确降级，绝不能返回一个看起来正常的空结果。
- **同一对象的组装逻辑只能有一个权威入口**，调用点越多，零件漏装的概率越大。
- **把外部依赖分成"必需/增强"两档**，分别设计失败语义，是分布式系统健壮性的基本功。

## Case 006 · 测试全过但进程永不退出（并发/生命周期）

> 状态：**已修复** ｜ 难度：★★★★☆ ｜ 涉及链路：Agent/测试 ｜ 收益：集成测试从"无限挂起"到 3.5 分钟干净退出

### ① 问题

跑 `pytest tests/integration`，命令**十几分钟不结束**，也看不到任何输出。进程 CPU 几乎为 0——不像在算，像在等。

**量化现象**：单测 5 秒全绿；集成测试挂起 > 13 分钟且无输出。

### ② 定位

这次定位用了一套组合工具，值得完整记下来：

**第 1 步：排除"慢"，确认"卡"。** `Get-Process` 看 CPU：十几分钟只累积了 26 秒 CPU 时间——不是在跑慢逻辑，是阻塞在某个等待上。

**第 2 步：看它在等谁。** `netstat -ano | findstr <PID>` 只有一个 ESTABLISHED 连接（Milvus 19530）。写独立脚本直连 Milvus 测 search：0.2 秒返回。**服务端没问题，问题在进程内部。**（注意：gRPC 会保持长连接，"有连接"不等于"在等这个连接"，别被误导。）

**第 3 步：直接看线程栈。** `pip install py-spy` 然后 `py-spy dump --pid <PID>`，真相立刻浮出：

```
Thread "MainThread":  threading._shutdown (threading.py:1590)     ← 在等别的线程结束
Thread "Thread-1 (_connection_worker_thread)":  aiosqlite/core.py ← 永远不退出
```

`MainThread` 已经跑完了 pytest（**测试其实是全过的**，只是输出被管道缓冲看不到），卡在解释器关闭阶段：Python 退出时 `threading._shutdown()` 会**等待所有非守护（non-daemon）线程结束**。而这个 aiosqlite 工作线程永远在等下一个任务——因为它的连接**从来没被关闭过**。

追到代码：`get_agent_app()` 里 `await aiosqlite.connect(...)` 建了检查点连接存进模块全局变量，没有任何关闭路径。aiosqlite 的实现是给每个连接起一个**非守护**工作线程——连接不关，线程不死，进程不退。

还有一个帮凶：测试用的 `httpx.ASGITransport` **不会触发 FastAPI 的 lifespan 事件**，所以"在 lifespan shutdown 里清理"对测试天然无效，必须在 fixture 里手动清理。

### ③ 优化

1. `graph.py` 增加 `close_agent_apps()`：集中关闭所有检查点连接并重置单例。
2. 接到两处：FastAPI lifespan 的 `yield` 之后（生产路径）；conftest 的 `api_client` fixture teardown（测试路径，因为 ASGITransport 不跑 lifespan）。

```python
async def close_agent_apps() -> None:
    for conn in _checkpointer_conns:
        await conn.close()          # 连接关闭 → 工作线程退出 → 进程可退出
    _checkpointer_conns.clear()
```

### ④ 验证

重跑集成测试：`13 passed, 4 skipped in 211s`，并且**进程在打印结果后立即退出**（之前是永不退出）。

**教训**：

- **"测试通过但进程不退出"几乎总是有非守护线程没被清理**。第一反应就该是 `py-spy dump` 看线程栈，比猜快一百倍。
- **起了什么就要关什么**：数据库连接、线程、子进程，创建时就要想好"谁负责关闭、什么时候关"。
- **测试替身和真实运行时行为有差异**（如 ASGITransport 不跑 lifespan）——清理逻辑要在两条路径都接上。
- 管道缓冲会造成"没有输出 = 没有进展"的错觉；长跑任务直接把输出重定向到文件再 tail，别用 `| tail` 守着。

## Case 007 · Reranker 下载被墙 + transformers v5 拆掉旧 API（环境/依赖）

> 状态：**已修复** ｜ 难度：★★★☆☆ ｜ 涉及链路：RAG/环境 ｜ 收益：精排环节从"降级跳过"变成真实工作，GPU warm 查询 87–718ms

### ① 问题

两个连环问题。第一个：reranker 模型（`BAAI/bge-reranker-v2-m3`）没在本地，运行时去 HuggingFace 下载，环境 SSL 不通，精排环节一直走 Case 005 的降级分支（score 恒 0）。第二个：把模型从 ModelScope 拉到本地、又给机器装了 CUDA 版 torch 之后，reranker 报了个新错：

```
AttributeError: XLMRobertaTokenizer has no attribute prepare_for_model
```

**量化现象**：任何带 rerank 的查询都落回 RRF 降级序；错误栈指向 FlagEmbedding 内部。

### ② 定位

第一问好办：既然 HuggingFace 不通，就走和 BGE-M3 一样的路——`modelscope download` 把模型拉到 `models/` 本地目录，配置指向本地路径。

第二问看 traceback：`FlagEmbedding/inference/reranker/encoder_only/base.py` 在调 `self.tokenizer.prepare_for_model(...)`。`prepare_for_model` 本是 transformers 分词器基类的方法——查版本发现环境里是 **transformers 5.14.1（v5 大版本）**，这个方法在 v5 被移除了，而 **FlagEmbedding 1.4.0（已是最新）还在调用它**。一句话根因：

> **上游大版本升级删了 API，下游库还没跟上——依赖树里"隐式传递依赖"升上去了，兼容矩阵断裂。**

FlagEmbedding 声明的是 `transformers>=...`（没有上限），于是包管理器在某次更新中把 transformers 带到了 v5，埋下这颗雷。

### ③ 优化

1. **模型本地化**：`modelscope download --model BAAI/bge-reranker-v2-m3 --local_dir models/models/BAAI--bge-reranker-v2-m3`，`RERANKER_MODEL` 指过去，彻底摆脱运行时外网依赖。
2. **版本钳制**：降回 transformers 4.57.6（`prepare_for_model` 还在），并且在 `pyproject.toml` 里显式写死 `"transformers>=4.50,<5"` + 注释说明原因——**不让下一个重建环境的人再踩一次**。

为什么不反过来升 FlagEmbedding？试过，1.4.0 就是最新版，上游还没适配 v5。等它跟上之后再放开上限。

顺带记录 GPU 化的配套改动：`DEVICE=cuda` + `USE_FP16=true`（6GB 显存下 fp16 让 BGE-M3 + reranker 只占约 2.1GB），`get_rag_engine()` 把 `use_fp16` 传给两个模型，入库脚本同样跟随配置。

### ④ 验证

1. 区分度测试：相关文档得分 0.8899，不相关文档 0.0083——精排真的在工作。
2. 全链路：warm 查询 87–718ms（CPU 时代 ~2.3s 且 score 恒 0）；"锐雯主C配什么装备"前三条全是锐雯文档（0.80–0.85）。
3. 回归：单测 120 绿、集成 13 绿（3 分 19 秒），`pyproject.toml` 钳制后依赖可复现。

**教训**：

- **传递依赖是隐形的兼容地雷**。核心库（FlagEmbedding）对 transformers 这种底座依赖没有上限时，要在项目层面替它钳住。
- **大版本号变更（4→5）默认视为破坏性**，升级前先查目标库的兼容声明。
- **环境修复要落到依赖声明里**（pyproject/requirements），只改当前环境等于没修——下个 clone 项目的人还会炸一遍。
