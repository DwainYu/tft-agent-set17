# 03 · 复现与进阶指南

> 这份文档面向**计算机专业的学生**，目标是让你在一台干净的机器上，
> 把这个项目从"**跑通**"到"**读懂**"再到"**改造**"和"**优化**"。
> 它是一条阶梯，每一级都有明确的"完成标志"，你可以自测是否达标。

```
阶段一 跑通  →  阶段二 读懂  →  阶段三 改造  →  阶段四 优化
（能演示）     （能讲清）      （能扩展）      （能改进）
```

**重要前提**：核心演示链路（提问 → 流式推理 → 出阵容卡片）**只需要 SQLite + 一个 LLM API**，不需要 Milvus / Neo4j / GPU。RAG 和图谱是"进阶可选"，它们不可用时系统会优雅降级（见 `01` 文档 2.3 节）。所以**别被那一堆外部服务吓退——你完全可以先把主干跑起来**。

## 阶段零：准备环境

### 必装

| 工具 | 版本 | 用途 | 说明 |
|------|------|------|------|
| Python | ≥ 3.11 | 后端运行时 | `pyproject.toml` 要求 `>=3.11` |
| uv | 最新 | Python 包管理 | 比 pip 快很多，项目用它管理依赖 |
| Node.js | ≥ 18 | 前端运行时 | 建议 LTS 版本 |
| Git | 任意 | 版本控制 | 拉代码、做改造练习 |

安装 uv（Windows PowerShell）：

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

### 可选（进阶才需要）

| 工具 | 何时需要 |
|------|---------|
| Docker Desktop | 想跑 Milvus / Neo4j（RAG 和图谱）时 |
| GPU + CUDA | 想本地加速 BGE-M3 编码时（CPU 也能跑，只是慢） |

### Windows 特别提示（踩过的坑，详见 `02` 案例集）

- 控制台打印中文/emoji 可能报 GBK 错。养成用 `python -X utf8` 运行脚本的习惯。
- 在 Git Bash 里别用 `taskkill /PID ...`（`/PID` 会被当成路径），改用 PowerShell 的 `Stop-Process`。

## 阶段一：跑通（目标：能演示）

### 1. 拉代码、装依赖

```bash
git clone <仓库地址> tft-agent-set17
cd tft-agent-set17

# 后端依赖（uv 会自动创建 .venv 并按 uv.lock 精确安装）
uv sync

# 前端依赖
cd frontend
npm install
cd ..
```

### 2. 配置环境变量

```bash
# 复制模板
cp .env.example .env
```

打开 `.env`，**最关键的是 LLM 配置**。项目的 Agent 有"双轨制"（见 `01` 文档 1.3 节）：

- 如果你**有**一个 OpenAI 兼容的 API（项目实际用的是 LongCat-2.0 的远程 API），填上：
  ```
  OPENAI_API_BASE=https://你的端点
  OPENAI_API_KEY=你的key
  LLM_MODEL=你的模型名
  ```
- 如果你**没有**，把 `OPENAI_API_BASE` 留空。系统会自动退化为**规则规划器**，依然能回答结构化问题（阵容/装备查询），只是没有 LLM 的自然语言润色和智能重试。

其余配置（SQLite 路径、JWT secret 等）默认值即可跑。`.env` 里的 `RIOT_API_KEY`、Milvus、Neo4j、vLLM 等，**第一阶段都不用管**。

> 注意：`.env` 含密钥，**绝不能提交到 git**（`.gitignore` 已忽略它）。

### 3. 启动后端

```bash
uv run uvicorn api.main:app --host 0.0.0.0 --port 8002
```

- 应用入口是 `api/main.py` 里的 `app` 对象（`app = FastAPI(...)`）。
- 端口用 `8002` 是为了避开常见占用；前端代理默认指向 `127.0.0.1:8002`（见 `frontend/vite.config.ts`）。如果你改用别的端口，记得同步改前端代理。
- 看到 `Uvicorn running on http://0.0.0.0:8002` 即成功。

**验证后端**：浏览器开 `http://127.0.0.1:8002/docs`，能看到 FastAPI 自动生成的 Swagger 接口文档，说明后端起来了。

### 4. 启动前端

另开一个终端：

```bash
cd frontend
npm run dev
```

Vite 会提示本地地址（通常 `http://localhost:3000`，可能是 IPv6 的 `[::1]`）。浏览器打开它。

### 5. 端到端验证

在对话框输入"**锐雯主 C 怎么搭**"，回车。你应该看到：

1. 思考过程面板逐阶段展开（理解问题 → 选择工具 → 执行查询 → ……）。
2. 最后弹出一张**阵容卡片**：一排英雄头像、若干羁绊标签、推荐装备、平均排名。

**完成标志**：能稳定地问一个英雄、出一张带英雄头像和羁绊的卡片。

> 如果卡片出来了但英雄头像显示不全——那是 `02` 案例集 Case 002 记录过的坑，检查 `HeroAvatar` 是否用了匹配原画比例（2:1）的宽矩形 + `object-top`。

### 阶段一常见报错速查

| 现象 | 原因 | 解决 |
|------|------|------|
| `uv sync` 很慢/失败 | 网络问题 | 配置 PyPI 镜像源 |
| 后端起不来，提示缺模块 | 依赖没装全 | 重新 `uv sync` |
| 前端能开但提问没反应 | 后端没起 / 端口不对 | 确认后端在 8002，前端代理指向一致 |
| 提问返回"规则规划"而非智能回答 | 没配 LLM API | 正常现象，填上 `OPENAI_API_BASE` 即可启用 LLM |
| 打印中文报 GBK 错 | Windows 控制台编码 | `python -X utf8 ...`（见 `02` Case 003） |

## 阶段二：读懂（目标：能讲清）

跑通之后，**不要急着读全部代码**。这个项目文件不少，从头读到尾会迷失。推荐"顺着一个请求的生命周期"去读，边读边在纸上画调用链。

### 推荐阅读顺序（约 2–3 小时）

**第 1 步：先读 `01-核心链路技术栈精讲.md`**，建立"Agent / RAG / 前端"三条链路的全局认知。这是地图，源码是地形。

**第 2 步：从后端入口往下追。** 按这个顺序读，每个文件只抓主干：

```
api/main.py            → 应用入口、路由挂载、SSE 端点在哪
  └ api/routers/*      → 找到 /ask 这个端点，看它怎么构造 AgentState、怎么流式返回
      └ api/agent/graph.py   → Agent 的拓扑：Planner→Executor→Critic→Reflect + 重试条件边
          ├ api/agent/state.py   → AgentState 有哪些字段（系统的"记忆"）
          ├ api/agent/nodes.py   → 四个节点各干什么（重点：双轨制、Critic 反馈闭环）
          └ api/agent/tools.py   → 11 个工具的注册表（重点：execute 的统一成功/失败契约）
```

**第 3 步：读前端如何消费 SSE。**

```
frontend/src/hooks/useSSE.ts        → 核心：六阶段协议、AbortController、累积器
  └ frontend/src/components/ChatArea.tsx   → 怎么发起提问、怎么管理会话
      └ frontend/src/components/CompCard.tsx + HeroAvatar.tsx  → 卡片怎么渲染
```

**第 4 步（可选）：读数据从哪来。**

```
scripts/mine_comps.py        → 怎么从对局 CSV 用 Jaccard 聚类挖出 56 套阵容
data_collection/scripts/*    → 怎么从 Riot API 采集原始对局数据
```

### 读懂的自测题

合上代码，能回答下面这些问题，才算"读懂"：

1. 一个 `/ask` 请求进来，后端依次经过哪几个 LangGraph 节点？
2. `AgentState` 里 `plan`、`tool_results`、`critique`、`should_retry` 分别由哪个节点写入？
3. Critic 判断"要重试"后，Planner 第二轮和第一轮有什么不同？（提示：反馈注入）
4. 为什么 `rag_search` 工具即使 Milvus 挂了也不会让整个请求失败？
5. 前端为什么用 SSE 而不是 WebSocket？`result` 阶段和其他阶段的数据有什么不同？
6. 阵容卡片里的"平均排名""样本量"这些数据，最初是怎么算出来的？

答不上来的，回到对应源码再读一遍。**能用自己的话讲出来，才是真懂。**

## 阶段三：改造（目标：能扩展）

读懂之后，通过"小改造"把知识变成肌肉记忆。下面几个练习由易到难，每个都对应一个真实的能力点。

### 练习 1：给 Agent 加一个新工具（理解工具注册）

在 `api/agent/tools.py` 里加一个工具，比如 `get_item_build_path(item_name)`，返回某件装备的合成路径。步骤：

1. 在 `_register_all` 里用 `self._register(name, description, parameters, fn)` 注册。
2. 写好 JSON Schema（`parameters`）——这份 Schema 会同时给 LLM 做 function-calling。
3. 实现 `fn`，从 SQLite 查数据，返回 dict。
4. 重启后端，在 Swagger 或前端提问验证 LLM 会不会选中它。

**你会学到**：工具如何被 LLM"看见"并调用，JSON Schema 的作用。

### 练习 2：改 Planner 的 prompt（理解 LLM 编排）

打开 `api/agent/llm.py` 里的 `PLANNER_SYSTEM_PROMPT`，调整它对"多工具组合"的引导（比如让它遇到"X 和 Y 搭配吗"时优先调 `calc_synergy`）。重启后观察 Planner 的工具选择是否变化。

**你会学到**：prompt 如何影响 Agent 决策，以及为什么 prompt 改动要配合"评测"（见阶段四）。

### 练习 3：给思考过程加一个阶段（理解 SSE 协议）

前后端各加一个新阶段，比如 `ranking`（在 `composing` 之后展示"正在排序候选阵容"）。需要改：后端的 SSE 事件发送、前端 `useSSE.ts` 的 `STAGE_ORDER` 和 `STAGE_LABELS`、思考面板组件。

**你会学到**：SSE 协议是前后端的"契约"，改一端必须同步改另一端。

### 练习 4：换一个 LLM（理解双轨制与解耦）

把 `.env` 的 `OPENAI_API_BASE` 指向另一个 OpenAI 兼容服务（如本地的 Ollama）。验证 Agent 是否照常工作。

**你会学到**：面向接口（OpenAI 兼容协议）编程的好处——换模型不用改代码。

## 阶段四：优化（目标：能改进）

这一阶段把 `02` 案例集的方法论真正用起来。

### 优化 1：应用 RAG 单例缓存（必做）

这是 `02` Case 001 留下的练习。按文档里的方案，给 `RAGEngine` 加 `lru_cache` 单例工厂，改掉 `tools.py` 里 `_rag_search` 的每次新建实例。然后用文档里的三种方式验证（第二次调用变快、"Loading BGE-M3" 日志只出现一次、超时场景消失）。

**注意**：这一步需要 RAG 真的能跑（Milvus 已起、模型已就位），否则你验证不到性能差异。如果环境不具备，可以先把代码改对，验证留给后面。

### 优化 2：给 RAG 建一个评测集（理解"测量先于优化"）

写 10–20 个开放式问题，人工标注每个问题"应该命中哪段知识"。用 Recall@K、MRR 量化当前检索质量。然后试着调 `top_k`、HNSW 的 `ef`、是否开 reranker，观察指标变化。

**你会学到**：为什么"没有评测集的 RAG 优化都是玄学"。

### 优化 3：给核心逻辑补单元测试（理解工程化）

项目有 `tests/` 目录和 pytest 配置（`pyproject.toml` 里定义了 `unit/integration/eval` 等 marker）。挑一个纯函数（比如 `nodes.py` 里的 `_parse_plan_from_text`，或 `engine.py` 里的 `_reciprocal_rank_fusion`）写单元测试。

```bash
uv run pytest -m unit
```

**你会学到**：什么样的代码"好测试"（纯函数、依赖注入），以及测试如何给你的改造兜底。

### 优化 4：工具并发执行（进阶）

把 `executor_node` 的串行 `for` 循环改成并发（`asyncio.gather`），让互不依赖的工具同时跑。前提：先把 SQLite 访问异步化、确认工具间无依赖。

**你会学到**：并发优化的前提条件，以及"为什么不能无脑并发"。

## 最后：给学习者的几条建议

**先跑通，再求甚解。** 不要试图一开始就理解每一行。先让系统在你手里"活"起来，建立直觉，再回头啃原理。

**改一行，看一次。** 做改造练习时，每次只改一个小地方，立刻验证效果。一次改太多，出了问题你不知道是哪行的锅。

**多问"为什么是它"。** 看到任何技术选型，用 `01` 文档的"选型三问"去拷问它。能说出 trade-off，才算掌握。

**把踩的坑记下来。** 用 `02` 的模板，把你遇到的问题写成案例。半年后回看，这是你成长最快的证据，也是你简历上"解决问题能力"的素材。

**接受"半成品"。** 这个项目有缺口（RAG 未验证、文档有漂移、测试不全）。这不是缺点，是给你的练习题。**能识别出一个系统的不足并提出改进方案，是比"会用一个系统"高一个层级的能力。**
