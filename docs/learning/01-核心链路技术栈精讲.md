## 0. 先看全局：一个请求的完整生命周期

在钻进任何一条链路前，先建立全局图景。当用户在前端输入"锐雯主 C 怎么搭"并回车，会发生这些事：

```
[前端] 用户提问
   │  POST /ask  (SSE 长连接)
   ▼
[FastAPI] 接收请求，构造初始 AgentState
   │
   ▼
[Agent · LangGraph]  Planner → Executor → Critic →(可重试)→ Reflect
   │   ├─ Planner:  决定调哪些工具（LLM function-calling，失败则退化为规则）
   │   ├─ Executor: 真正执行工具（查 SQLite / 查 Milvus / 查 Neo4j）
   │   ├─ Critic:   评估结果够不够好，不够好就让 Planner 重来
   │   └─ Reflect:  把工具结果组织成自然语言 + 结构化卡片
   │  每完成一个阶段，通过 SSE 推一个事件给前端
   ▼
[前端] 逐阶段展开"思考过程"，最后渲染阵容卡片
```

记住这张图。下面三条链路，分别对应图里的 **Agent（大脑）**、**RAG（记忆/检索）**、**前端（表达）**。

涉及的核心源码：

|------|---------|
| Agent | `api/agent/graph.py`、`state.py`、`nodes.py`、`llm.py`、`tools.py` |
| RAG | `api/services/rag/embedding.py`、`reranker.py`、`engine.py`、`graph_store.py` |
| 前端 | `frontend/src/hooks/useSSE.ts`、`components/ChatArea.tsx`、`ChatMessage.tsx`、`CompCard.tsx` |

# 链路一：Agent 编排（LangGraph）

## 1.1 它解决什么问题

最简单的 LLM 应用是"一问一答"：用户提问 → 模型回答。但 TFT 问答有个根本矛盾：

> **模型本身不掌握"实时、准确的结构化数据"。** 你问"锐雯主 C 的阵容"，模型可以编一套听起来合理的答案，但英雄可能是错的、羁绊可能凑不齐、平均排名是瞎猜的。

解决办法是让模型**学会使用工具**：它不直接回答，而是先决定"我该查什么"，调用查询工具拿到真实数据，再基于数据回答。这就是 **Agent（智能体）** 的核心思想——**LLM 负责推理和决策，工具负责提供事实**。

更进一步，一次工具调用往往不够。"锐雯主 C 怎么搭"理想情况下要同时查阵容和查装备；第一次查的结果可能不全，需要换个角度再查。所以我们需要一个能**多步推理、能自我纠错**的编排框架。

## 1.2 为什么用 LangGraph，而不是自己写循环

你完全可以自己写一个 `while` 循环来实现"规划 → 执行 → 检查 → 重试"。那为什么用 LangGraph？

**事实层面**，LangGraph 提供了三样自己写很麻烦的东西：

第一，**显式的状态机**。它强迫你把"系统现在处于什么阶段""有哪些状态字段"写清楚。看 `api/agent/state.py`：

```python
class AgentState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
    question: str
    direction: str | None
    entities: list[dict[str, Any]]
    plan: list[ToolCallPlan]          # Planner 产出的工具调用计划
    tool_results: list[dict[str, Any]] # Executor 产出的结果
    critique: str                      # Critic 的评语
    should_retry: bool                 # 是否重来一轮
    iteration: int                     # 循环计数，防止死循环
    final_answer: str
    card_data: dict[str, Any] | None   # 给前端的结构化卡片
    error: str | None
```

这个 `AgentState` 就是整个系统的"记忆"。每个节点（node）是一个纯函数 `(state) -> 部分状态更新`，LangGraph 负责把更新合并进全局状态。**好处是：任何时刻系统处于什么状态、下一步能去哪，都是可枚举、可调试、可可视化的。** 自己写循环，这些状态往往散落在局部变量里，出了 bug 很难复盘。

第二，**条件边（conditional edge）**。看 `api/agent/graph.py` 的拓扑：

```python
graph.add_edge(START, "planner")
graph.add_edge("planner", "executor")
graph.add_edge("executor", "critic")
graph.add_conditional_edges(          # ← 关键：Critic 之后分叉
    "critic",
    should_retry,                      # 这个函数返回 "retry" 或 "done"
    {"retry": "planner", "done": "reflect"},
)
graph.add_edge("reflect", END)
```

画出来就是：

```
START → planner → executor → critic ─→ reflect → END
            ↑                    │
            └────── retry ───────┘   (条件边，受 iteration 上限保护)
```

"如果结果不够好就回到 planner 重来"——这个逻辑用条件边表达，比在循环里塞 `if` 清晰得多，而且天然受 `AGENT_MAX_ITERATIONS` 保护，不会死循环。

第三，**checkpointer（检查点持久化）**。`graph.py` 里用 `AsyncSqliteSaver` 把每一步状态存进 SQLite：

```python
conn = await aiosqlite.connect(settings.CHECKPOINT_DB)
checkpointer = AsyncSqliteSaver(conn)
_agent_app = compile_agent(checkpointer=checkpointer, ...)
```

这带来三个能力：跨请求恢复对话状态、崩溃后从最近检查点恢复、以及 **human-in-loop**（`interrupt_before=["executor"]` 可以在执行工具前暂停，让人审查计划再继续）。这些如果自己实现，工作量不小。

**判断层面**（这是我的观点）：对一个学习项目，LangGraph 的"显式状态机"价值远大于它的"框架便利性"。它逼着你把 Agent 的思考过程结构化，这恰好和产品的核心卖点——**把"虾神在想什么"展示给用户**——完美契合。前端那个三阶段思考面板，本质上就是 Agent 状态机的可视化。

**trade-off**：LangGraph 有学习曲线，且是个相对年轻、API 还在变的框架。如果你的逻辑极其简单（一问一答、无工具），用它属于杀鸡用牛刀。

## 1.3 项目里怎么实现的：四个节点

### Planner（规划）——LLM 与规则的"双轨制"

`planner_node` 的职责是：给定问题，产出一个**工具调用计划**（`list[ToolCallPlan]`，注意是列表，支持一次调多个工具）。

这里有一个非常值得学的设计——**双轨制**：

```python
def planner_node(state):
    llm = get_llm()
    if llm is not None:
        return _llm_plan(llm, state, ...)   # 主轨：LLM function-calling
    plan = _rule_based_plan(...)             # 备轨：关键词规则
    return {"plan": plan, ...}
```

- **主轨**：用 `llm.bind_tools(schemas)` 把 11 个工具的 JSON Schema 喂给模型，让模型自己决定调哪些工具、传什么参数。这是 OpenAI function-calling 的标准用法。
- **备轨**：如果 LLM 不可用（没配 API、网络挂了、超时），退化为 `_rule_based_plan`——一套基于关键词和实体匹配的规则逻辑。

**为什么这么设计？** 这是工程上的"优雅降级（graceful degradation）"。LLM 是增强项，不是必需项。哪怕模型服务全挂了，系统靠规则也能给出基本可用的答案。**永远不要让一个外部依赖的故障，导致整个系统不可用**——这是后端设计的一条铁律，你会在项目里反复看到这个模式（RAG、Neo4j 工具都是这样）。

### Executor（执行）——工具注册表

`executor_node` 遍历计划，逐个调用工具：

```python
registry = ToolRegistry(conn)
for step in plan:
    result = registry.execute(step["tool"], step.get("args", {}))
```

`ToolRegistry`（`api/agent/tools.py`）是 11 个工具的注册中心。每个工具注册时带一份 JSON Schema，这份 Schema 有两个用途：给 LLM 做 function-calling（`openai_schemas()`），以及描述参数。11 个工具是：

```
query_comps / query_items / query_specific / search_items   ← 查 SQLite 阵容/装备
rag_search / graph_query                                     ← 查 Milvus / Neo4j（会优雅降级）
get_champion_info / get_trait_info / get_item_info          ← 查静态详情
calc_synergy / get_version_meta                             ← 计算/统计
```

注意 `execute` 的返回结构永远是 `{"success": bool, "data": ..., "error": ...}`，工具内部异常被 `try/except` 兜住，不会炸掉整个图。**统一的成功/失败契约**，让上游 Critic 能用一致的方式判断结果好坏。

### Critic（评审）——自我纠错的心脏

这是整个 Agent 最有意思的部分。`critic_node` 评估工具结果，决定要不要重来：

```python
if iteration >= max_iter:           # 硬上限，防死循环
    return {"should_retry": False, ...}
llm = get_llm()
if llm is not None:
    return _llm_critique(...)        # 让 LLM 判断结果质量，输出 RETRY/DONE
# 规则兜底：只要有一个工具返回了有效数据，就算通过
has_data = any(r.get("success") and r.get("data") for r in results)
return {"should_retry": not has_data, ...}
```

而"重来"不是简单重复——`_llm_plan` 在 `iteration > 0` 时会把**上一轮的反馈**注入 prompt：

```python
if iteration > 0:
    retry_context = "\n\n【上一轮反馈】\n"
    retry_context += f"已尝试的工具: {tried}\n"
    retry_context += f"评审意见: {critique}\n"
    retry_context += f"上一轮结果摘要: {summary}\n"
    retry_context += "请根据反馈调整工具计划……不要重复完全相同的计划。"
```

这构成了一个**反馈闭环**：Planner 出方案 → Executor 执行 → Critic 打分并给出改进意见 → Planner 拿着意见调整方案。这正是 ReAct（Reasoning + Acting）模式的工程化落地，也是 Agent 区别于"单次 LLM 调用"的本质。

### Reflect（反思/组装）——把数据变成回答

`reflect_node` 把工具结果组织成最终答案。它做两件事：从 `query_comps` 结果里提取 `card_data`（给前端渲染卡片），以及用 LLM（或模板兜底）生成自然语言总结。

## 1.4 怎么优化这条链路

给你几个真实的优化方向，从易到难：

**（1）减少 LLM 往返次数。** 当前 Planner、Critic、Reflect 各调一次 LLM，一轮就是 3 次，重试一轮再 +3。每次都是网络往返 + 推理延迟。优化思路：把 Critic 的判断"内联"进 Planner（让 Planner 自评），或把 Reflect 和 Critic 合并。**代价**是单次 prompt 变复杂、可控性下降——这又是个 trade-off。

**（2）给工具调用加并发。** `executor_node` 现在是串行 `for` 循环。如果计划里有多个互不依赖的工具（比如同时查阵容和查装备），可以用 `asyncio.gather` 并发执行。**前提**是工具之间无依赖、且底层连接支持并发（当前 SQLite 连接是同步的，需要先异步化）。

**（3）Critic 的判断标准要可观测。** 现在 Critic 是否触发重试，很大程度取决于 LLM 的"心情"。建议把每次的 `critique` 和 `should_retry` 落库，积累一批数据后分析"什么样的结果容易被判 RETRY"，再反过来优化 Planner 的 prompt。**先测量，再优化**——这是 `02` 案例集反复强调的方法论。

# 链路二：RAG 检索增强（BGE-M3 + Milvus + Reranker）

## 2.1 它解决什么问题

工具能回答"结构化"问题（锐雯的阵容、劫的装备），但回答不了"开放式"问题：

- "新手第一次玩应该注意什么？"
- "这个版本为什么大家都玩游侠？"
- "暗星羁绊的设计思路是什么？"

这些问题没有对应的 SQL 查询，答案散落在攻略文章、版本说明、社区讨论里。**RAG（Retrieval-Augmented Generation，检索增强生成）** 就是为此而生：

```
用户问题 → 把问题转成向量 → 在知识库里找最相似的几段文本 → 把文本塞进 prompt → 让 LLM 基于这些"证据"回答
```

核心价值：**让 LLM 基于你提供的、可更新的私有知识回答，而不是凭训练时的记忆瞎编。** 知识变了，只要更新知识库，不用重新训练模型。

## 2.2 为什么是 BGE-M3 + Milvus + Reranker 这套组合

RAG 有三个环节，每个环节都有选型。我们逐个用"选型三问"拆解。

### 环节一：把文本变成向量——为什么用 BGE-M3

**它解决什么**：计算机不能直接比较"两段话意思像不像"。Embedding 模型把文本映射成一个高维向量（BGE-M3 是 1024 维），意思相近的文本，向量在空间里距离就近。这样"找相似"就变成了"找距离最近的向量"。

**为什么是 BGE-M3**：看 `api/services/rag/embedding.py`，它一次编码产出**三种**表示：

```python
return {
    "dense": output["dense_vecs"],        # 1024 维稠密向量（语义相似）
    "sparse": output["lexical_weights"],  # 稀疏词权重（类似 BM25，关键词匹配）
    "colbert_vecs": output["colbert_vecs"], # 多向量（词级别细粒度交互）
}
```

- **dense（稠密）** 擅长"语义相似"——"新手入门"和"萌新攻略"词不同但意思近，稠密向量能捕捉到。
- **sparse（稀疏）** 擅长"精确关键词"——专有名词如"奥瑞利安·索尔"，语义模型可能不认识，但稀疏向量靠字面匹配能命中。

**这就是"混合检索"的由来**：单靠语义会漏掉精确关键词，单靠关键词会漏掉语义改写，两者互补。BGE-M3 的"M3"就代表 Multi-lingual（多语言）、Multi-granularity（多粒度）、Multi-functionality（多功能），一个模型同时给你这三种向量，省得部署三个模型。

**trade-off**：BGE-M3 模型很大（磁盘约 4.3GB，内存 fp32 加载约 2.3GB+），加载慢、占资源。这是它为"全能"付出的代价——也正是 `02` 案例集里那个性能 bug 的根源。

### 环节二：存向量、查向量——为什么用 Milvus

**它解决什么**：知识库可能有几万、几十万段文本，每段是 1024 维向量。用户提问时要在毫秒级找出"最相似的 Top-K"。这是经典的**最近邻搜索（ANN）** 问题，普通数据库的 `ORDER BY 距离` 全表扫描根本扛不住。

**为什么是 Milvus**：它是专门的向量数据库，看 `engine.py` 里建的索引：

```python
# 稠密向量用 HNSW 索引（一种近似最近邻图结构）
self._collection.create_index("dense",
    {"index_type": "HNSW", "metric_type": "COSINE", "params": {"M": 16, "efConstruction": 200}})
# 稀疏向量用倒排索引
self._collection.create_index("sparse",
    {"index_type": "SPARSE_INVERTED_INDEX", "metric_type": "IP"})
```

HNSW 用"分层导航小世界图"把搜索从 O(n) 降到近似 O(log n)，这是向量检索能在大规模数据上做到毫秒级的算法基础。**Milvus 同时原生支持稠密 + 稀疏两种向量**，正好匹配 BGE-M3 的混合检索需求，这是选它而非纯用 pgvector 的关键原因。

**trade-off**：Milvus 是个独立的外部服务，要单独部署、单独运维（项目用 Docker Compose 起）。对一个学习项目，这是不小的复杂度。轻量替代是 SQLite + 一个纯 Python 的向量库（如 `sqlite-vec`），但规模和性能上限低。

### 环节三：精排——为什么还要 Reranker

**它解决什么**：向量检索（尤其 HNSW）是"近似"的，且为了召回率会先捞回较多候选（代码里是 `top_k * 4`）。这些候选里有些"看起来像、其实不相关"。Reranker 做二次精排，把真正相关的排到前面。

**为什么用 cross-encoder（BGE-Reranker）**：这里有个重要概念区分——

- **向量检索用的是 bi-encoder（双塔）**：query 和 doc 各自独立编码成向量，再比距离。优点是 doc 向量可以预先算好、检索快；缺点是 query 和 doc 之间没有"交互"，理解深度有限。
- **Reranker 用的是 cross-encoder（交叉编码）**：把 `[query, doc]` 拼在一起送进模型，让两者在注意力层充分交互，判断更准。缺点是慢——每对 query-doc 都要过一次模型，没法预计算。

所以工程上的标准打法是：**用快但粗的 bi-encoder 召回候选，用慢但准的 cross-encoder 精排 Top-K**。看 `engine.py` 的 `query()` 就是这个流水线：

```python
encoded = self.embedding.encode_query(query_text)          # 1. 编码 query
dense_hits = self.milvus.dense_search(...)                 # 2. 稠密召回
sparse_hits = self.milvus.sparse_search(...)               #    稀疏召回
candidates = self._reciprocal_rank_fusion(dense_hits, sparse_hits)  # 3. 融合两路结果
scored = self.reranker.rerank(query_text, unique, top_k=top_k)      # 4. cross-encoder 精排
```

其中 `_reciprocal_rank_fusion`（RRF，倒数排名融合）是个很巧的算法：它不需要知道稠密分和稀疏分各自的量纲（两者分数尺度根本不同，没法直接相加），只用"排名"来融合——某文档在两路里排名都靠前，融合分就高。公式是 `score = Σ 1/(k + rank)`。**用排名而非分数来融合异构结果**，这是个值得记住的通用技巧。

## 2.3 优雅降级：外部服务挂了怎么办

`tools.py` 里的 `_rag_search` 和 `_graph_query` 都用 `try/except` 包住，Milvus/Neo4j 不可用时返回"服务暂不可用"而不是抛异常：

```python
def _rag_search(self, query, top_k=5):
    try:
        ...
        docs, latency = engine.query(query, top_k=top_k)
        return [{"content": d.content, ...} for d in docs]
    except Exception as exc:
        logger.warning("rag_search unavailable: %s", exc)
        return [{"content": f"RAG 服务暂不可用: {exc}", "score": 0, "metadata": {}}]
```

这保证了：即使 Milvus 没启动，Agent 依然能用 SQLite 工具回答结构化问题，只是开放式问题答不了。**系统的可用性不应该被最脆弱的那个组件绑架。**

## 2.4 怎么优化这条链路

**（1）模型单例缓存（最重要，详见 02 案例集）。** 当前 `_rag_search` 每次调用都 `BGEEmbedding()` 新建实例，导致几个 G 的模型每次重新加载。做成单例后，模型只加载一次。**这是从"几十秒"到"几百毫秒"的量级优化。**

**（2）量化与设备。** 当前 `device="cpu"`、`use_fp16=False`。如果有 GPU，把模型放 GPU 上、开 fp16，编码速度能提升一个量级，内存也减半。`embedding.py` 的构造函数已经预留了这两个参数。

**（3）检索质量评估。** RAG 最难的不是"跑通"，而是"检索得准不准"。建议建一个小型评测集（一批问题 + 期望命中的文档），用 Recall@K、MRR 等指标量化检索质量，再调 `top_k`、HNSW 的 `ef`、是否开 reranker 等参数。**没有评测集的 RAG 优化都是玄学。**

# 链路三：前端流式交互（React + SSE）

## 3.1 它解决什么问题

Agent 推理可能要好几秒（多轮工具调用 + 多次 LLM）。如果前端"转圈圈等 10 秒后一次性出结果"，体验很差，用户会以为卡死了。

更好的做法是**流式输出**：后端每完成一个阶段，立刻把进度推给前端，前端实时展示"虾神正在理解你的问题……正在挑选工具……正在组织回答……"。这就是你在产品截图里看到的那个可折叠的"思考过程"面板。

## 3.2 为什么用 SSE，而不是 WebSocket

实现服务端推送有两个常见选择：

- **WebSocket**：全双工，浏览器和服务器可以互相随时发消息。功能强，但协议复杂、需要维护连接状态、对代理/负载均衡不友好。
- **SSE（Server-Sent Events）**：基于普通 HTTP，**服务器单向**推给浏览器。协议极简（就是 `Content-Type: text/event-stream` 的长连接），天然支持断线重连，走标准 HTTP 所以基础设施友好。

**判断**：TFT 问答的场景是"用户问一次，服务器单向推一串进度，最后给结果"——**完全是单向推送，不需要全双工**。用 WebSocket 属于过度设计。SSE 恰好够用、且简单。这是个"用最简单的工具解决当前问题"的好例子。

**trade-off**：SSE 只能服务器→浏览器单向，且默认基于 HTTP/1.1 时每个域名连接数有限。如果未来要做"服务器主动向所有用户广播""实时双向协作"，才需要考虑 WebSocket。

## 3.3 项目里怎么实现的：六阶段协议

后端和前端约定了一套 SSE 事件协议，共六个阶段。看 `frontend/src/hooks/useSSE.ts`：

```typescript
export const STAGE_ORDER: SSEStage[] = [
  'understanding',   // 理解问题
  'tool_selection',  // 选择工具
  'tool_execution',  // 执行查询
  'tool_done',       // 查询完成
  'composing',       // 整理结果
  'result',          // 最终结果（唯一携带结构化 card 的阶段）
];
```

前五个阶段只携带 `content`（一段描述文字，对应思考面板的一行），**只有 `result` 阶段携带 `data.card`**（结构化阵容卡片数据）。这个设计很关键：**过程是文本，结果是结构**——前端对两者用完全不同的渲染方式。

`useSSE` 这个 hook 是前端的核心，它做了几件事：

```typescript
const ask = useCallback(async (question, direction?, conversationId?) => {
  setLoading(true); setStage('understanding');      // 重置状态
  abortRef.current = new AbortController();          // 支持中途取消
  const reasoningAcc = {};                           // 累积各阶段文字
  return new Promise((resolve, reject) => {
    postAsk({ question, direction, conversation_id }, (event) => {
      if (event.stage === 'result' && event.data) {
        setCard(event.data.card); ...                // 收到结果，渲染卡片
        resolve({ card, results, summary, reasoning });
      } else if (event.content) {
        reasoningAcc[event.stage] = event.content;   // 累积过程文字
        setReasoning({ ...reasoningAcc });
      }
      setStage(event.stage);                         // 更新当前阶段
    }, abortRef.current.signal);
  });
}, []);
```

几个值得学的点：

- **`AbortController`**：让用户能在推理中途取消请求，`cancel()` 一调用就中断 SSE 连接。这是流式交互的必备体验。
- **用累积器 `reasoningAcc` 而非直接 setState 拼接**：因为 React 的 `setState` 是异步的，闭包里拿不到最新值，所以用一个局部对象累积，再整体 `setReasoning({...reasoningAcc})`。这是个常见的 React 流式更新陷阱。
- **Promise 包装**：把"基于回调的 SSE"包装成"基于 Promise 的 ask()"，让调用方可以 `await`，并在 `result` 到达时 `resolve`。

## 3.4 卡片渲染：结构化数据的组件化

`result` 阶段的 `card` 是一个复合结构（英雄列表、羁绊、装备、纹章、平均排名等）。前端用 React 组件化拆解：`CompCard`（整体）→ `HeroAvatar`（英雄头像）→ `EmblemBlock`/`ArtifactBlock`（纹章/神器）等。

这里有个真实的踩坑（已修复）：英雄原画是 256×128 的横图（2:1），最初 `HeroAvatar` 用 48×48 正方形 + `object-cover` 裁剪，把英雄裁掉了。修复是改成 64×48 的宽矩形 + `object-top`，匹配原画比例、显示上半身。
> 教训：**UI 还原要先看素材的真实尺寸比例**，而不是想当然用正方形。这类问题靠"看截图"才能发现，单元测试测不出来。

## 3.5 怎么优化这条链路

**（1）SSE 心跳与超时降级。** 弱网下长连接可能中断。可以加心跳事件保活，并设计降级：超时后一次性返回完整结果，而不是让用户看到半截。

**（2）渲染性能。** 每次 `setReasoning` 都会触发重渲染。阶段多、更新频繁时，可以用 `React.memo` 隔离思考面板和卡片，避免卡片跟着每次进度更新重渲染。

**（3）错误可视化。** 当前 `error` 状态有了，但用户侧的错误提示可以更友好（区分"网络错误""服务降级""无结果"）。

## 4. 三条链路如何协作（回到全局）

现在把三条链路串起来，再看一遍那个请求：

1. **前端**用 SSE 发起请求，进入"等待流式推送"状态。
2. **Agent** 的 Planner 决定调 `query_comps`（结构化）；如果是个开放问题，则调 `rag_search`。
3. 若调 `rag_search`，就进入 **RAG** 链路：BGE-M3 编码 → Milvus 混合检索 → Reranker 精排 → 返回相关文本。
4. Critic 评估结果，不够好就带着反馈让 Planner 重来（可能从"查阵容"改成"查专属 + 语义检索"）。
5. Reflect 组装出自然语言 + 卡片数据。
6. 每个阶段通过 SSE 推给前端，前端逐步展开思考过程，最后渲染卡片。

**一句话记忆**：Agent 是大脑（决策调什么），RAG 是记忆（检索知识），前端是表达（流式呈现）。三者通过"工具"和"SSE 协议"两个契约解耦——大脑不关心记忆怎么存的，表达不关心大脑怎么想的，各层只认契约。这种**面向契约的解耦**，是整个系统能独立演进的根本。

## 5. 本节小结：选型三问回顾

| 技术 | 解决什么 | 为什么是它 | 代价 / 优化方向 |
|------|---------|-----------|----------------|
| LangGraph | 多步推理 + 自我纠错的 Agent 编排 | 显式状态机、条件边、检查点持久化 | 学习曲线；优化点是减少 LLM 往返、工具并发 |
| BGE-M3 | 文本→向量（语义+关键词） | 一个模型给 dense+sparse+colbert，支持混合检索 | 模型大、加载慢 → 单例缓存、量化、上 GPU |
| Milvus | 大规模向量毫秒级检索 | HNSW 索引 + 原生稠密/稀疏双支持 | 外部服务运维成本；轻量替代 sqlite-vec |
| Cross-encoder Reranker | 召回后精排 | query-doc 交互，判断更准 | 慢，只能用于 Top-K 精排 |
| SSE | 服务器单向流式推送 | 比 WebSocket 简单，契合单向场景 | 仅单向；优化点是心跳保活、超时降级 |
| React 组件化 | 结构化卡片渲染 | 组件复用、状态管理成熟 | 流式更新注意重渲染性能 |
